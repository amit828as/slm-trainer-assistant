# Data Policy

Good SLM behavior starts with boring data discipline.

## Source Records

Keep records for training data sources. Every example should identify whether it is `manual`, `synthetic`, `public_doc_derived`, `user_notes`, or `rejected`.

## Split Discipline

Separate train, eval, and stress sets. Do not mix eval examples into training data. Eval contamination makes a model look better without proving it generalized.

## Licensing

Avoid copyrighted or unclear-license sources. Public documentation can be useful, but examples derived from it should be marked and should preserve source references when possible.

## Rejected Examples

Keep rejected examples when useful for analysis. Rejections can reveal unsafe patterns, unclear prompts, bad labels, or source-quality problems.

## Provenance Labels

Use `source_type` consistently:

- `manual`: written by project maintainers.
- `synthetic`: generated by a model and reviewed before use.
- `public_doc_derived`: derived from public documentation with a recorded source.
- `user_notes`: based on user-owned notes.
- `rejected`: kept for analysis, not training.
